# MCPデータ流トレーサー 設計書

Nov 24, 2026 · @小林

## 概要とゴール

MCPのツール呼び出しをプロキシで記録し、「あるツールの出力が、後続のどのツール呼び出しに流れたか」を自動で追跡して、複数のMCPサーバーをまたぐ情報の流れをグラフにする基盤を作る(仮称: `mcp-flow`)。

**解きたい問題**: エージェントが複数のMCPサーバーをつなぐと、あるサーバーが返した情報(社内文書、トークン、個人情報)が別のサーバー(メール送信、HTTP、ファイル書き込み)の引数に流れても、誰も気づけない。既存ツールは通信の記録・再生、脆弱性スキャン、レイテンシ計測が中心で、呼び出しをまたぐ情報の流れを追う層は、調べた範囲では見つからなかった。

### ゴール
- 1セッション分のツール呼び出しから、出力から入力へのデータ依存グラフを自動で作る
- 「機密と印を付けたソース」から「外部送信系ツール」に届く経路を検出して報告する
- 結果をCLI、Mermaid/DOT、MCPサーバー(AI自身が自分のセッションを調べる)の3経路で取り出せる
- 既存のサーバーやクライアントのコードは変えず、設定のコマンドをプロキシに差し替えるだけで使える

### 非ゴール
- 攻撃ペイロードを送るスキャナにはならない(受動的な観測に徹する)
- LLM内部の推論は追わない。見えるのはプロトコル上の入出力だけ
- 通信を止めるゲートウェイ機能は初期スコープ外(まず観測と報告)
- 言い換えられた情報の追跡は確率的な推定で、完全な追跡は保証しない

## 先行事例との差別化

既存ツールは「1回の呼び出し」を記録・計測・攻撃・監査するものが中心で、呼び出し同士をつなぐデータ依存を追うものは、今回の検索では見つからなかった。

| 種類 | 代表例 | できること | mcp-flowとの違い |
| :--- | :--- | :--- | :--- |
| 録画・再生・差分 | mcptape、mcp-recorder、mcp-rec、agentape | 通信を記録してオフラインで再生、挙動の差分を比較 | 目的は通信の再現。情報の流れは追わない |
| 観測プロキシ | mcpscope | リクエスト、レイテンシ、エラーを記録し、本番で録ってCIで再生 | 1呼び出し単位の計測。呼び出し間の依存は見ない |
| OTel計装 | Elastic、Grafana MCP | ツール呼び出しのスパンやメトリクスを出力 | サーバー側の計装。サーバーをまたぐデータ依存は範囲外 |
| セキュリティスキャナ | MCPFuzz、MCPFang、mcpsec、trustmcp | 説明文の静的解析、攻撃ペイロードの送信、ファジング | 能動的に攻撃する。mcp-flowは実トラフィックを受動的に観測する |
| ゲートウェイ | Gravitee、Composio | 認証認可、監査ログ、ポリシー強制 | 「誰が何を呼んだか」の記録。内容がどこへ流れたかは追わない |

## 全体アーキテクチャ

### 3層(記録・解析・取り出し)
クライアントとサーバーの間にプロキシを1つ挟み、通信を改変せず中継しながら全メッセージをSQLiteに追記する。解析層はあとから何度でも再計算でき、結果はCLI、ファイル、読み取り専用のMCPサーバーの3経路で取り出す。

1. **① 記録(リアルタイム)**: MCPクライアント <-> `mcp-flow` プロキシ <-> MCPサーバー群 (`messages` へ追記)
2. **② 解析(あとから再計算できる)**: SQLite保存 (`messages`) -> 派生: 断片化 (`calls` と `fragments`) -> 段階的マッチ (`完全 -> 部分 -> 正規化 -> 類似度 -> 埋め込み`) -> フローグラフ (`辺 = 内容一致の観測 + 機密ラベル`)
3. **③ 取り出し**: CLIレポート (`mcp-flow report`) / ファイル出力 (`Mermaid / DOT / JSON`) / 読み取り専用MCPサーバー (本文は既定で伏せる)

## データモデル

生のメッセージを追記専用のログとして保存し、呼び出し・断片・フロー辺はそこから何度でも再計算できる派生データにする。マッチング手法を変えるたびに派生層だけ作り直せば、同じトレースで手法の比較実験が回せる。

| 層 | テーブル | 中身 | 再計算 |
| :--- | :--- | :--- | :--- |
| 生ログ | `sessions`, `servers`, `messages` | JSON-RPCメッセージを連番・時刻・方向付きでそのまま保存 | 不可(一次データ) |
| 呼び出し | `calls` | `tools/call` のリクエストとレスポンスを `id` で対にした1行 | 可 |
| 断片 | `fragments` | 引数と結果のJSONを葉の文字列まで分解し、パスと正規化文字列を保持 | 可 |
| フロー | `flows` | 出力断片から入力断片への辺。一致の種類、スコア、一致範囲 | 可 |
| ラベル | `labels`, `tool_roles` | 機密の印、ツールの役割(ソース / シンク / 中立) | 可(ルールから) |

```sql
CREATE TABLE sessions(id TEXT PRIMARY KEY, started_at REAL, client TEXT, note TEXT);
CREATE TABLE servers(id TEXT PRIMARY KEY, session_id TEXT, name TEXT, command TEXT, transport TEXT);
CREATE TABLE messages(seq INTEGER PRIMARY KEY, session_id TEXT, server_id TEXT, ts REAL,
                      dir TEXT,      -- 'c2s' | 's2c'
                      kind TEXT,     -- 'request' | 'response' | 'notification'
                      method TEXT, rpc_id TEXT, body TEXT);
CREATE TABLE calls(id INTEGER PRIMARY KEY, session_id TEXT, server_id TEXT, tool TEXT,
                   req_seq INTEGER, res_seq INTEGER, t_start REAL, t_end REAL, is_error INTEGER);
CREATE TABLE fragments(id INTEGER PRIMARY KEY, call_id INTEGER,
                       side TEXT,    -- 'in' (arguments) | 'out' (result)
                       json_path TEXT, text TEXT, norm TEXT, len INTEGER, hash TEXT);
CREATE TABLE flows(id INTEGER PRIMARY KEY, src_frag INTEGER, dst_frag INTEGER,
                   kind TEXT,        -- 'exact' | 'substring' | 'normalized' | 'minhash' | 'semantic'
                   score REAL, src_span TEXT, dst_span TEXT);
CREATE TABLE labels(id INTEGER PRIMARY KEY, target_kind TEXT, target_id INTEGER, label TEXT, source TEXT);
CREATE TABLE tool_roles(server TEXT, tool TEXT, role TEXT, PRIMARY KEY(server, tool));
```

**設計上の約束**:
- `messages` は追記のみ。JSONLとしてエクスポートでき、他ツールのトレース形式との変換口を残す
- データは既定でローカルのSQLiteファイルのみ。外部送信しない
- 保存前に伏せ字(redaction)をかけられる。伏せ字をかけると指紋一致の精度が落ちるため、ハッシュ化した断片だけ残すモードも用意する

## 指紋エンジン

出力断片を、あとの入力断片と安い手法から順に照合し、前段で十分な確信が出たら後段は走らせない。高い段階ほど「言い換え」を拾えるが、誤検出とコストも増える。

| 段階 | 手法 | 拾えるもの | 主な誤検出 | コスト |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 完全一致(正規化前後のハッシュ) | 値がそのままコピーされた(ID、トークン、URL) | 短くて一般的な値(true、1) | 最小 |
| 2 | 部分文字列一致(最小長を超える共通部分) | 出力の一部が引数に埋め込まれた | 定型句、共通のヘッダ | 小 |
| 3 | 正規化一致(空白、大文字小文字、Unicode、URLエンコード、base64、JSONエスケープを外して比較) | 形式変換されて渡った | 正規化で不必要に衝突 | 小 |
| 4 | n-gramシングルとMinHashの類似度 | 一部が編集・並び替えされた | 一般的な語句の重なり | 中 |
| 5 | 埋め込み類似(オプトイン) | 要約や言い換え | 話題が近いだけの誤検出 | 大 |

### 誤検出を抑える仕組み
- 情報量の低い断片(短い文字列、真偽値、空文字、エントロピーが低い値)は照合対象から外す
- セッション内で頻出する値(スキーマのキー名やツール名)は重みを下げる
- 出力が入力より前に起きていること(連番の大小)を必須にする
- スコア = 一致の種類、一致した長さ、値の希少性から計算し、しきい値未満は低信頼として区別する
- すべての辺に一致範囲(証拠)を残し、人間が見て判断できるようにする

**辺の意味**: プロトコル上で見えるのは、LLMがどの出力を参照して引数を作ったかではなく、「内容が一致した」という観測事実だけ。したがって辺は「依存の可能性」を示し、因果の証明ではない。レポートとグラフにもこの区別を明記する。

## フローグラフと出力

ノードはツール呼び出し、1本の辺は「出力から入力へ内容が一致した」ことを表す。同じ呼び出し対の間で複数の断片が一致したときは1本にまとめ、最高スコアと一致断片数を持たせる。

### 機密ラベルとツールの役割
- 設定ファイルでサーバー名・ツール名のパターンに役割(ソース / シンク / 中立)とラベルを付ける
- 内容としてはAPIキー、メールアドレス、トークン形式を正規表現で検出して断片にラベルを付ける
- 利用者が「このツールの出力は機密」と手動で指定できる

**危険経路の検出**: ラベル付きのソースから、シンク役のツール呼び出しへ到達する経路をグラフ探索で列挙する。経路のスコアは辺スコアの最小値を基本にし、辺がどれだけ確かかを左右する弱い辺を比較できるようにする。

### 出力は3系統

| 出力 | 内容 |
| :--- | :--- |
| CLI | `mcp-flow report <session>`: 危険経路の一覧と証拠。`mcp-flow graph <session> --format mermaid` |
| ファイル | Mermaid、DOT、JSON(他ツールとの連携用) |
| MCPサーバー | 読み取り専用。`list_sessions`、`get_flow_graph`、`find_paths(source_label, sink_role)`、`explain_edge(edge_id)` |

## マイルストーン (M0〜M6)

| マイルストーン | やること | 完了の条件(ゲート) |
| :--- | :--- | :--- |
| **M0 土台** | スキーマと JSON-RPC の切り出し | テストが通り、DBが作れる |
| **M1 記録** | stdio プロキシと `messages` 保存 | 模擬サーバー経由で `calls` が記録される |
| **M2 最初のグラフ** | 断片化、完全・部分一致、Mermaid出力 | 合成シナリオ3本で期待フローが出る |
| **M3 ラベルと危険経路** | 機密ラベル、検出器、`report` コマンド | 負例シナリオで誤検出が出ない |
| **M4 精度と評価** | 正規化・MinHash 一致と評価ハーネス | 手法ごとの適合率と再現率が出る |
| **M5 MCP公開** | 読み取り専用の MCP サーバー | AIが自セッションの経路を取得できる |
| **M6 拡張** | 埋め込み類似(任意)と Streamable HTTP | 実クライアントで通しの検証が済む |
